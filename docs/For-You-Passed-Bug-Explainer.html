ClickUp 14zmk4dkx0v · For You passed profiles issue

Why For You still says “Passed”

When a user runs low on new profiles, Aisle gives profiles they passed long ago a second chance. Those profiles come back, but in For You they still carried the old “Passed” label, so the user could not comment or like them.

Bug: re-shown profile labelled “Passed” Django part (cache clear) · live on prod Rails part (label) · only on develop_new Backend-only → Android and iOS

This page teaches the whole feature from scratch: what Rails does, what Django does, which databases they share, and where the bug and the open questions sit. All code shown is quoted from aisle_new@develop_new and django_algorithm@django_master; behaviour read from code is to be confirmed with Dev.

Start · Words you need

Eight terms

U, P1U is the user we test with. P1, P2… are the profiles U sees and acts on.
PassU taps ✕ on P1. Saved as a row in Postgres user_passes.
Hidden listPostgres action_hiddens_partition_N. “Never show P1 to U again.” Every pass adds a row.
Blocked bitmapDjango’s own copy of the hidden list, stored as a file blocklists/<ref>.rbm. Used to filter Discover.
Pass resetCalled “repeat pass” in code. Django takes some old passes out of the bitmap so they show again.
For You (FY)Daily list of 6 (men) / 8 (women) cards, built by Rails and cached in Redis.
Card labeldisplay_message: Reported, Blocked, Comment Sent or Passed. Any label sets can_send_comment=false.
KafkaMessage queue. Rails and Django talk to each other through it instead of calling each other directly.
Part 1 · The system

Two backends, five data stores

Rails (aisle_new) is the main Aisle API that the app calls. It owns passes, the hidden list and For You. Django (django_algorithm) is the matching engine. It builds Discover, keeps the blocked bitmap and runs the pass reset.

Blue = Rails. Purple = Django. Dashed purple = what Django touches during a reset (reads passes, clears the Redis cache, writes Mongo). Dashed boxes are Django-only stores.

Part 1 · Data stores

Where every piece of data lives

Store Name / key What’s in it Written by Read by
Postgres user_passes One row per pass: initiator_id (U), partner_id (P1), created_at, can_show_in_recent_passes, tags.tab_name. Passing P1 again adds a new row. Rails Rails label · Django reset
Postgres action_hiddens_partition_<U÷1000> “Don’t show P1 to U”. Status: created → enqueued_kafka → consumed_django → synced. Rails Rails For You · Django to build bitmap
Redis <PRODUCT>_<env>_closest_matched_profile_<ref> U’s For You: refs (pool), todays_list, pass_list, start_date… Expires one week after it was built. Rails Rails · deleted by Django on reset
Django disk blocklists/<ref>.rbm Blocked bitmap: everyone U must not see in Discover. Django Django Discover
Django disk blocklists/<ref>_passed.rbm Profiles given a second chance by a reset. Treated as “don’t block”. Django Django
Mongo repeat_pass_shown_partner_ids One doc per user: user_id, shown_partner_ids (all ever re-shown), created_at, updated_at = last reset time (UTC). Django Rails label (fix) · Django eligibility
Mongo debug_logs Event repeat_pass_bitmap_created per reset, with the partner IDs and time. Django Django 30-minute throttle
The For You Redis key is built the same way on both sides: Rails Cache::Key.create_key uses PRODUCT_NAME + "_" + Rails.env, Django create_key uses the PRODUCT_NAME and RAILS_ENV environment variables. If those differ on a server, Django deletes a key Rails never reads. That is worth one question to Dev.
Part 2 · Rails (aisle_new)

What happens when U passes P1

The app calls POST /V1/pass_user with P1’s ref and the tab_name (for_you, discover, concierge). Rails does four things.

  1. Add P1 to U’s hidden list (Postgres).
    app/models/action/hidden.rbRuby 
    def fetch_table_name initiator_id
  "action_hiddens_partition_#{initiator_id / 1000}"   # U=12345 → partition_12
end

def add_entry initiator_id, partner_id
  if not_exists?(initiator_id, partner_id)
    create!(initiator_id: initiator_id, partner_id: partner_id)
    # after_commit :graph_entry → sends it to Django via Kafka (step 4)
  end
end
  2. Save the pass (Postgres user_passes). There is no “already passed” check, so a second pass makes a second row.
    app/models/user_pass.rb · pass_user / create_entryRuby 
    can_show_in_recent_passes = tab_name == 'for_you' ? false : true
create!(initiator_id: initiator_id, partner_id: partner_id,
        can_show_in_recent_passes: can_show_in_recent_passes,
        tags: { 'tab_name' => params['tab_name'], 'ref' => params['ref'] })
  3. Update U’s For You cache (Redis). From For You: P1 goes into pass_list and leaves the pool. From Discover/Concierge: P1 is removed from today’s list and a replacement is sampled.
    app/models/user_pass.rbRuby
    if %w[discover concierge].include?(tab_name)
  Algorithm::TopMatch.update_for_you_cache current_profile, other_user.ref
else
  Algorithm::TopMatch.add_to_pass_list current_profile.ref, other_user.ref
end
  4. Tell Django through Kafka, so Django adds P1 to U’s blocked bitmap.
    app/models/action/hidden.rb · graph_entryRuby 
    data_for_redis = { user_id: initiator_id, blocked_user_id: partner_id, ref_id: profile.ref }
KafkaProducer.produce('test_graph_sync', { data: data_for_redis, action_hidden: true })
# then: UPDATE action_hiddens_partition_N SET status = enqueued_kafka

    This only runs when the config flag Configuration::Constant.fetch_sync_graph is on. Keep this in mind for Q5.

Part 2 · Rails

How For You is built

The app calls GET /V1/users/fetch_top_matched_profiles. Rails first looks in Redis. Only if the cache is missing (or the user changed preferences) does it rebuild from Postgres.

The rebuild path (top) is the one a reset forces, because Django deletes the cache.

app/models/algorithm/top_match.rbRuby 
def fetch_profiles_list profile, params = {}
  refs = fetch_cached_refs profile          # Redis
  if !refs.present?
    refs = Strategy_3.fill_cache_from_db profile   # rebuild
  end
  results, liked_by = profile.filter_top_matches_list refs
  profile.create_top_matches_response results, liked_by, params
end
app/models/profile.rb · used by Strategy_3Ruby 
scope :not_from_hidden_list, ->(user_id) {
  table_name = Action::Hidden.fetch_table_name user_id
  joins("LEFT JOIN #{table_name}
         ON #{table_name}.partner_id = profiles.user_id
        AND #{table_name}.initiator_id = #{user_id}")
  .where("#{table_name}.partner_id IS NULL")  # P1 excluded
}
Part 2 · Rails

How the card label is chosen

For each profile in today’s list, Rails checks four things in order. The first match wins and disables comment.

Order Check Label (display_message)
1 U reported P1 Reported
2 U blocked P1 Blocked
3 U commented on P1 Comment Sent
4 U passed P1 (this is where the bug was) Passed
– none of the above null, can_send_comment: true
Before the fix
user_pass.rbRuby
def has_passed_profile? initiator_id, partner_id
  by_initiator(initiator_id).by_partner(partner_id)
    .first.present?      # EVER passed?
end
After the fix (Rails 70e220f)
user_pass.rb + profile.rbRuby
last_pass_reset_at = MongoRepeatPassShown.last_reset_at(user_id)
def has_passed_profile?(initiator_id, partner_id, after: nil)
  passes = by_initiator(initiator_id).by_partner(partner_id)
  passes = passes.where('user_passes.created_at > ?', after) if after.present?
  passes.first.present?  # passed SINCE last reset?
end
app/models/mongo_repeat_pass_shown.rb (Rails reads what Django writes)Ruby 
store_in collection: 'repeat_pass_shown_partner_ids'
def self.last_reset_at(user_id)
  where(user_id: user_id).only(:updated_at).first&.updated_at   # nil if no doc → old behaviour
end
Key point for Q5: the fix depends completely on Django writing updated_at into Mongo. No Mongo doc means after: nil, and Rails falls back to “ever passed”, which is the bug.
Part 3 · Django (django_algorithm)

The blocked bitmap

Django filters Discover with a compact file of user IDs per user: a bitmap (“roaring bitmap”, .rbm). It is fed by the Kafka messages Rails sends on every hidden-list entry.

profiles/kafka_consumer_v2.py → neo4j_model.py · add_blockedPython 
if action_hidden == True:
    return self.process_action_hidden(decoded)      # → profile_model.add_blocked(user_id, blocked_user_id, False, ref_id)

def add_blocked(self, user_id, blocked_user_id, coming_from_redis_stream=False, ref_id=None):
    is_bitmap = bitmap_file_exists(ref_id)          # blocklists/<ref>.rbm on disk?
    if is_bitmap:
        add_single_blocked(ref_id, blocked_user_id)  # add one ID
        remove_from_passed_bitmap(ref_id, blocked_user_id)
    else:
        all_blocked = get_blocked_profiles_postgres_user_id(ref_id)   # first time: copy whole hidden list
        all_blocked.add(blocked_user_id)
        add_all_blocked(ref_id, all_blocked)         # creates the file (skips IDs in <ref>_passed.rbm)
        remove_from_passed_bitmap(ref_id, blocked_user_id)
profiles/blocklist_manager.pyPython
STORAGE_DIR = "blocklists"
def get_bitmap_path(user_id):
    return os.path.join(STORAGE_DIR, f"{user_id}.rbm")   # called with the ref → blocklists/<ref>.rbm
def bitmap_file_exists(user_id):
    return os.path.isfile(get_bitmap_path(user_id))
So the bitmap file is created the first time Django processes a hidden-list message for U. If Django never got one (sync flag off, Kafka or consumer failure, file lost or not on that server), U has no bitmap file. This is the condition behind Q5.

When a reset fires

While building U’s Discover feed, Django counts profiles in the “last seen 30–90 days” bucket. If fewer than 50 remain, it sends a reset message to itself through Kafka.

Part 3 · Django

What a reset does, line by line

Django’s Kafka consumer sees repeat_pass: true and calls handle_repeat_pass_trigger. This is the function behind Q5.

profiles/neo4j_model.py · handle_repeat_pass_trigger (trimmed)Python 
# A. throttle: skip if a reset ran in the last 30 minutes (reads Mongo debug_logs)
mins = DebugLogMiddleware.get_minutes_since_latest_event(user_id, "repeat_pass_bitmap_created")
if mins is not None and mins <= 30: return

# B. which old passes get a second chance
partner_ids = get_recent_passes_with_activity_check_optimized(user_id)
if not partner_ids: return

# C. remember them in a separate "passed" bitmap + write the log event
add_all_blocked(f"{ref}_passed", set(partner_ids))
DebugLogMiddleware.log(event_type="repeat_pass_bitmap_created", user_id=user_id, entries=partner_ids)

# D. ONLY IF the main bitmap file exists:
if bitmap_file_exists(ref):
    set_all_blocked(ref, set(get_blocked(ref)) - set(partner_ids))  # D1 unblock in Discover
    MongoRepeatPassShown.add_shown_partner_ids(user_id, partner_ids) # D2 Mongo: updated_at = now
    delete_closest_matched_profile_data(ref)                         # D3 delete FY cache (fix PR #117)
profiles/profile_data_access.py · step B querySQL 
SELECT up.partner_id
FROM user_passes up
JOIN profiles p ON p.user_id = up.partner_id
WHERE up.initiator_id = :user_id
  AND p.last_seen_window >= NOW() - INTERVAL '90 days'   -- partner active
GROUP BY up.partner_id
HAVING COUNT(*) = 1                                       -- passed exactly once
   AND MAX(up.created_at) <= NOW() - INTERVAL '14 days'  -- at least 14 days ago
-- then in Python: drop IDs already in Mongo shown_partner_ids (one second chance only)
profiles/mongo_repeat_pass_shown.py · step D2Python 
cls._get_collection().update_one(
    {"user_id": int(user_id)},
    {"$addToSet": {"shown_partner_ids": {"$each": normalized_partner_ids}},
     "$set": {"updated_at": now},            # ← the reset time Rails reads (UTC)
     "$setOnInsert": {"created_at": now}},
    upsert=True)

5. When can the bitmap file be missing?

Sync switched offRails only sends hidden entries to Kafka when fetch_sync_graph is on.
Message not processedKafka or consumer failure: the action_hiddens row stays at created / enqueued_kafka, never synced.
File not on that serverFiles sit in a local blocklists/ folder. If several Django servers each have their own disk, the one handling the reset may not have U’s file.
File removedDisk cleanup, redeploy to a new machine, or a reconcile script that hasn’t run yet.

Part 6 · Testing

All questions for Dev, explained

Q1Is the Rails label change live on prod?

Only Rails sets “Passed” (Part 2). The Django fix only clears the cache. Without 70e220f on prod, Rails still checks “ever passed”.

AskIs 70e220f deployed to prod Rails? If not, how does the Django cache delete alone remove the label?

Q2Can you force a reset?

A reset fires only when Discover’s 30–90-day bucket has fewer than 50 profiles, at most once per 30 minutes (Part 3). A normal test account may never reach that.

AskCan you trigger handle_repeat_pass_trigger for our test user (there is a script, verify_repeat_pass_mongo_exclusion.py, that calls it), or set up an account with a small pool?

Q3Which profiles come back?

Only profiles passed once, at least 14 days ago, by partners active in the last 90 days, and not shown by an earlier reset (the SQL in Part 3).

AskIs that the intended rule? Can we get a test account whose passes on internal test profiles are 14+ days old?

Q4How does a reset profile get back into For You?

The reset changes Django’s bitmap, not the Postgres hidden list. When Rails rebuilds For You it uses not_from_hidden_list, and P1 is still in that list. By the code, P1 should return in Discover but not in For You.

AskWhat path brings a reset profile into For You on prod? Otherwise we may wait for a card that can never appear.

Q5Mongo update and cache clear only if the bitmap exists

See Part 5. If blocklists/<ref>.rbm is missing, the reset skips the Mongo time and the cache delete. Rails then shows “Passed” again.

AskIs this intended? Does the file exist for our test account? Is the folder shared across Django servers?

Q6Prod test accounts

On prod, a pass, like or comment reaches a real person. We need internal accounts on both sides.

AskOne tester plus 3–4 internal partner accounts with matching preferences, and how to log in on prod.

Q7Reset time and re-shown list

A reset is invisible in the app. We need the time (to compare with pass times) and the profile IDs (to know which cards to look for).

AskAfter each reset, share debug_logs → repeat_pass_bitmap_created (time + entries) and Mongo repeat_pass_shown_partner_ids.updated_at for U (UTC; IST = +5:30).

Q8Same Redis key on both sides?

Django deletes <PRODUCT_NAME>_<RAILS_ENV>_closest_matched_profile_<ref>. Rails reads <PRODUCT_NAME>_<Rails.env>_….

AskDo PRODUCT_NAME and RAILS_ENV on prod Django match prod Rails?
