# Coverage matrix — Aisle PII facade

What the 98 service tests cover, per facade endpoint. Architecture under test:
**QA automation → Aisle PII facade (Bearer token) → PII service → PII DB (read-only checks)**.

Each cell holds one of:

- **Test IDs.** A test marked _(blocked)_ exists and runs as soon as its dependency is resolved. Until then it is
  reported as BLOCKED with the real reason (never passed, never failed).
- **Blocked – BQ-xx (dependency).** No test can be written or run until Dev answers.
- **Not planned – reason.** Nothing meaningful to test in that cell. This is QA's judgement, NOT a Dev-confirmed
  "Not Applicable": no feature has been confirmed as unsupported by Dev yet, so no cell is marked N/A.

Question IDs refer to [backend-open-questions.md](backend-open-questions.md). The target is the **PII service's**
behaviour; the facade (token, tenant, signing, routing, edge) is temporary QA scaffolding and is tested only as far as
the test harness needs it. NAME, EMAIL and free-text keys are accessible (since 2026-10-01).

**Status on 2026-10-01:** 98 tests. 85 can run now. 13 are blocked: DB access BQ-04: 5 (POC-003, AISLE-DB-001,
AISLE-DB-002, AISLE-DB-004, AISLE-DB-005) · temporary-phone expiry BQ-28: 2 (AISLE-TR-005, AISLE-TR-007 — the shortest
lifetime is 300 s) · and one each: bulk-read maximum BQ-18 (AISLE-BR-013), second revoke BQ-33 (AISLE-FT-004), Unicode

## Gaps (known, deliberate or waiting on Dev)

- **Clean-up:** there is no delete API, so every written fake record stays on staging and is reported as
  "left behind" (BQ-10, which also asks whether a delete / right-to-erasure API is planned).
- **Facade-only behaviour is out of scope:** token checks, tenant injection, token scheme variants, a token in the URL,
  broken JSON (400 “Invalid JSON”), missing or extra body parts and omitted settings (the facade rebuilds the body),
  the reply envelope, wrong HTTP methods, unknown paths, request IDs, CORS / security headers, plain http://, body-parsing and body-size limits, extra body
  properties and response times are produced by the temporary facade or the Cloudflare edge, not the PII service,
  so they are not tested (user decision 2026-10-01).
- **Attack-looking names blocked at the edge:** names with SQL-like or path-like text never reach the PII service
  (403 from the edge firewall), so their storage cannot be tested through the facade (BQ-35).
- **Duplicates:** duplicate user IDs or field names return duplicate items; AISLE-BR-004 records the count but does
  not assert de-duplication; AISLE-RD-008 / AISLE-BR-008 lock the observed behaviour.
- **Layer not confirmed (kept):** user-ID trimming (AISLE-WR-012, BQ-34), field names in any case (AISLE-WR-018,
  BQ-44) and the no-store header (AISLE-SEC-006, BQ-39) could come from the PII service or the facade.
- **Kept although they touch the facade:** AISLE-HLT-001 (the harness needs a ready check) and AISLE-SEC-003 (QA log
  and report hygiene).
- **Not-ready health (503)** cannot be triggered safely on staging.
- **Phone length limits:** only refusals are tested with made-up values (5, 7 and 16 digits, AISLE-NRM-003); the
  accepted edges (8 and 15 digits) would need more approved test numbers, so they are not tested.
- **Temporary-phone expiry:** AISLE-TR-005 and AISLE-TR-007 need an expired phone; the shortest lifetime is 300 s, so
  they stay Blocked until Dev offers a shorter test lifetime or accepts a 5-minute test (BQ-28).
- **Encryption proof:** DB tests only show a value is not stored readable. Proving encryption needs the storage
  format from Dev (BQ-04). What is audited is open (BQ-30).
- **Success-reply internals:** whether `tenant_id` and `key_version` belong in success replies is open (BQ-29);
  AISLE-SEC-005 checks error replies only.
- **NAME search:** undocumented; AISLE-SR-015 only records that it answers (BQ-32).
- **Token, tenant and token-scope checks** (missing / wrong / malformed token, tenant sent by the caller, whether
  the QA token may read any user ID) were removed on 2026-10-01: they test the temporary facade, not the PII service
  (user decision). Requirements FR-AUTH-01, FR-AUTH-02, FR-ISO-01 and FR-ISO-02 are marked out of scope.
- **Rate limiting:** not probed; QA does not load-test staging (BQ-43).
- **Expired or revoked token:** not tested — the test token is QA-only and the facade is temporary (QA decision
  2026-10-01).
- **Echo of submitted values in 422 replies:** known finding BQ-08 (low priority), no active test. Requirement
  FR-SEC-01 stays visible as a gap.
- **Second revoke of a free-text key:** 404 or 200 is not decided; AISLE-FT-004 is Blocked until Dev answers (BQ-33).
- **Out of scope by design:** PII-service signing, caller IDs, per-caller permissions and tenant selection — Aisle
  handles these internally and QA tests only the facade.
